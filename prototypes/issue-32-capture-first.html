Capture first. Reconcile in repository space.

Does a Pull View-gated, lazy Capture combine safely with a commit-anchored isolated-checkout Sync Base and Git-style merge or replacement — while keeping the repository untouched until Apply?

This is a disposable simulation. It uses an in-memory one-file Sync Unit. Review, Capture, merge, edit, and approval never mutate the simulated repository; only Apply does.

    How to read the prototype
    • Pull Views decide whether work exists. They are never merge operands.
    • Capture returns typed repository representation: Missing or Present(bytes). Raw/default Capture is lazy unless the live Pull View itself is Capture-backed.
    • Sync Base stores a commit anchor plus the path payload from an isolated checkout. Exact and conservative bases use the same merge algorithm.
    • Proposal is a transactional draft. Editing it changes only the draft. Apply is the sole source mutation seam.
    • After a changed Pull is applied, the base remains unchanged. A later qualifying Push or fresh no-change Pull establishes committed ancestry.
